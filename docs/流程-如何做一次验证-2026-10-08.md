# 如何做一次验证 —— 操作手册

> **目的**：让下一个接手的人**不用重新摸索**就能从头跑完一次验证。
> **本文所有命令都在本机实测过（2026-10-08）**，写的是**实际结果**，不是"应该能跑"。
> 定位：**操作手册**（怎么做）。至于**为什么这么设计**，去各层 PRD；**能测什么**，去
> `关于策略/Tugboat/11-验证-数据体检报告-2026-10-08.md`。

---

## 0. ★ 先决定：你要回答哪个问题（**选错层 = 白干**）

| 你要回答的问题 | 走哪条路 | 为什么 |
|---|---|---|
| 「这套**选股规则**选出来的股票，后续是不是**比随机好**？」 | **A. 截面随机对照**<br>`factor-layer/evaluate/placebo/` | 答案在**横截面**上 —— **同一天里**跟随机比 |
| 「这套**交易策略**（按信号买卖）赚不赚钱、扛不扛得住？」 | **B. 时序回测**<br>`backtest/` | 答案在**时间序列**上 —— PnL / 回撤 / 分段 |
| 两者都要 | **先 A 再 B** | 截面不过 ⇒ 选股没信息 ⇒ 时序回测只会测出"成本" |

> ⚠️ **两条路不能互相替代**（形状相反，见 `factor-layer/docs/PRD/02-…` §二）。
> **别用 RankIC 代替随机对照，也别用随机对照代替回测。**
> 两者失效模式不同：IC 高 ≠ 选出来的那批比随机好；对照过了 ≠ 扣成本后还赚钱。

**另一件必须先钉死的事**：**规则/参数要在看结果之前写死**（预注册）。
跑完再改阈值 = 把验证变成自欺。本仓的做法是**把阈值钉进契约与测试**（见 §4）。

## 1. 前置：把数据更新到最新

```bash
cd data-layer
.venv/bin/python pipeline.py --daily --skip-adjust   # 日常（实测约 15 秒）
.venv/bin/python pipeline.py --daily                 # 每周一次（实测约 3 分钟，含复权因子）
```

**不用想任何事**：盘中/盘后跑都行（自动取「最后一个已收盘交易日」）；已最新则跳过；跑一半断了再跑接着补。

**验证数据到位**（下游取数的唯一入口）：

```bash
.venv/bin/python -m provide.cli days | tail -3      # 最新交易日
.venv/bin/python -m provide.cli stocks --day 2026-10-07   # 该日票池
```

### ⚠️ 坑 1：**必须用一个"真有快照"的交易日取票池**

实测（2026-10-08）：

| 调用 | 返回 |
|---|---|
| `read_stocks('2026-10-07')['stocks']` | **270 只** ✅ |
| `read_stocks('2026-10-08')['stocks']` | **1 只**（`TIGO`）⚠️ |

**2026-10-08 那天美股还没收盘**，库里只有 `chain` 的几个代码 ⇒ `stocks()` 几乎返回空。
**它不报错**，只是安静地给你 1 只 —— 后面所有统计都建在 1 只上。

⇒ **取票池前先 `days()` 看一眼，确认那一天是真交易日**（用 `stocks --day` 直接验更稳）。

## 2. 路线 A：截面随机对照（**先做这条**，它便宜且最可能是瓶颈）

### A1. 缺因子？加一个（2 处改动，框架零改动）

```
1. 新建 factor-layer/factor/implementations/<因子名>.py
   → 定义类（spec 七要素 **全必填**）+ `register_factor(...)`
2. 在 factor-layer/factor/implementations/__init__.py 加一行 `from . import <因子名>`
```

**⚠️ `role` 必须选对**（第七要素）：

| role | 什么时候用 |
|---|---|
| `alpha` | 可独立评估的因子（收益 / 波动 / RSI…）—— **会被 IC 评估** |
| `screening` | **筛选原料**（均线值、均线距离…）—— 排序它 = 排序价格 ⇒ **不参与 IC** |

**⚠️ 指标的公式写在 `factor/technical_indicators.py`**（唯实现点），不要在因子文件里重算。

**验证**：
```bash
cd factor-layer
.venv/bin/python tests/test_factor.py                 # 27 项（含 warm-up / 七要素 / role）
.venv/bin/python tests/test_technical_indicators.py   # 17 项（手推校验）
```

> **加规则的验证**：`tests/test_placebo_rsi_rule.py`（**13 项**）是参照模板 ——
> 它给**每个条件**造一只"只差这一条"的票 ⇒ 五个条件各有一条测试盯着它**有没有真的在拦人**。
> 只验"能选出一批股票"是**弱的**：把条件写反的实现照样能选出东西。

### A2. 写选择规则

```
新建 factor-layer/evaluate/placebo/implementations/<规则名>.py
在同上 __init__.py 加一行
```

规则必须实现三样（`Selection` 协议）：

| 成员 | 要求 |
|---|---|
| `name` | 非空字符串；**跑参数变体要显式给不同的 `name`**（注册表要不同的键）|
| `requires` | `tuple[str, ...]` —— 依赖的**因子名**。**建议由参数算出**，别写死全集 |
| `params` | `Mapping` —— **会进报告的指纹**（半年后能回答"当时用的哪个阈值"）|
| `select(data) -> set[str]` | 只读 `data.factor(名)` / `data.today(名)` |

**R1 的纪律（两条硬的）**：

- **拿不到未来**：`run_selection` 已把因子表**物理切成 `[:day]`**，你**想违规也没有数据**。
- **不许重算原始指标**（RSI 本体归因子层）；**差分 / 比较 / 布尔组合是允许的**。

**写规则时顺手加 `diagnose()`**：返回**漏斗计数**（每个条件后剩几只）。
它在"某天一只都没选出来"时能一眼指出**卡在哪一条**（见 A4）。

### A3. 跑对照

对照有一条**正式命令**（`factor-layer/run_placebo.py`）：

```bash
cd factor-layer
.venv/bin/python run_placebo.py                    # 默认规则 + 全窗口（实测 38s）
.venv/bin/python run_placebo.py --iterations 200 --start 2025-06-01   # 冒烟
.venv/bin/python run_placebo.py --selection <规则名> --cost 0.0003
```

**它替你处理了三件容易错的事**（都会**打印出来**，不闷着做）：

| 你不用想 | 它怎么做 |
|---|---|
| 该用哪天的票池？ | 自动取**库里最后一个有快照的交易日**，取不到像样的就**往前找**并打印一行说明 |
| 窗口要多长？ | 默认从 `2022-05-03`（票池跳到 287 只那天）起 —— **用满**，否则一半样本是预热 |
| 成本是多少？ | `--cost` **印在报告头部** —— 改它 = 改实验（判决③直接受它影响）|

**库内入口**（自己写脚本时用）：`evaluate.placebo.baseline_runner.run_placebo(...)`
—— `cost_rate` / `sampling` **必填无默认**（承 C3），漏传直接 `TypeError`，
**不会**悄悄用 0。

⚠️ 用库内入口时**必须先 `import evaluate.placebo.implementations`**，
否则报"注册表为空"（注册是**显式动作**，与 `factor.implementations` 同款设计）。

### ⚠️ 坑 2：**预热会吃掉大半个窗口**（最容易白跑的一条）

实测：400 天面板 + 默认 `rise_window=260` ⇒ **只有 139 天能用**，
其中 104 天有选中（75%）—— 剩下那些"空日"**大半是预热**，不是规则太苛刻。

| 因子 | 预热期 |
|---|---|
| `off_low260` / `ret260` | **260 天** |
| `off_low150` | 150 天 |
| 其余 | 14–60 天 |

⇒ **窗口长度 = 你想要的可用天数 + 最长预热期**。
本仓有 **1,112 天**（2022-05-03 起）⇒ 用满窗口可得 **约 850 天**可用。
**别为了快就砍窗口** —— 砍到 400 天，一半的样本是预热期。

### A4. 怎么读报告

```
══ 随机对照报告：rsi_tight_consolidation ══
  ── 样本量（先看这个）──      ← ★ 先看这里，样本不够就别读后面的数
  交易日        : N / M（有效 / 总数）
  ── 两侧的绝对水平（不混）──
  真实平均收益 / 陪考平均收益 / 真实扣成本后   ← ★ 判据③看"真实扣成本后"
  ── 配对结果（相对优势，★ 同一天内比）──
  配对差值均值     ← ★ 判据② 看逐日配对（不是总平均相减）
  排位             ← ★ 判据①（门槛 95%）
  胜率             ← 描述统计，**不作门槛**（60–70% 就是好成绩）
  ── 判决：通过 / 说不清 / 不通过 ──
  已知偏差         ← ★ 幸存者偏差告警，**每次都要带着读**
```

**三道判据缺一不可**：① 排位 ≥95% ② 前后半段都为正 ③ **真实侧扣成本后为正**。

> ⚠️ 判据③ **看的是绝对收益，不是配对差值** —— 因为**配对差值对成本免疫**
> （`(real−c) − (null−c) = real−null`）。这条是落地时对契约的修正，见 02-PRD §五 R3。

### ★ 读结论时要带的三条偏差（**每条都有实测数字**，不是泛泛而谈）

| # | 偏差 | 实测 | 怎么读 |
|---|---|---|---|
| 1 | **幸存者偏差** | 票池 270 只**只增不减**、`n_ended_early = 0` | 报告自带告警：**「不显著」可信、「显著」不可信** |
| 2 | **过滤层缺失**<br>（规则源自的资料有、我们做不了）| 市值 `<$1B` 仅 **13/270**、50 日均额 `<$10M` 仅 **17/270**、行业剔除 **≈0** ⇒ 合计 **约 5–7%** | **不必因此否掉实验**，但**要带在结论里**。配对设计让两侧同池 ⇒ 这类噪声**部分抵消**（但规则有条件挑选 ⇒ 抵消**不完全**）|
| 3 | **命中数少** | 命中日**平均 2.4 只**（最多 9；75% 的日子有命中）| 从 270 只里随机抽 2 只 vs 你选的 2 只 ⇒ **噪声极大** ⇒ **必须读 `k_per_day_median`**，别只看排位 |

**"为什么某天一只都没选出来？"** 用规则自带的漏斗：

```python
rule.diagnose(data)   # {'universe': 270, 'after_rsi_calm': 9, ...}
```
实测卡点：**条件① 砍掉 96.8%**（269.6 → 8.7）—— 那是规则的灵魂，**不是 bug**。

### ⚠️ 坑 3：每天只选 2–3 只时，结论会**非常不稳**

实测该规则（400 天面板 / 可用 139 天）：**命中日平均 2.4 只、最多 9 只**，
且只有 **104/139 = 75%** 的日子有命中。
从 270 只里随机抽 2 只 vs 你选的那 2 只 —— 噪声极大 ⇒
**必须在报告里读出 `k_per_day_median`**，别只看排位就下结论。

> 想提高把握：**用满窗口**（1,112 天 ⇒ 可用约 850 天），样本翻 6 倍。

## 3. 路线 B：时序回测（`backtest/`）

### ★ B0. 如果目标是**某个具体交易系统**（不是玩具策略）—— 用 `run_tugboat.py`

`run_backtest.py` 只跑**单标的、逐只独立**的信号策略（`momentum` 那类）。
**它装不下**「横截面选股 + 共享资金 + 按 R 定仓 + 路径依赖出场」的**组合级**系统 ——
那需要 `backtest/trade_simulator.py`（事件驱动、组合级）。

第一个走通这条路的例子是 Tugboat「突破交易 2.0」：

```bash
# ★ 用 factor-layer 的 venv（它装了 pandas/numpy）
factor-layer/.venv/bin/python run_tugboat.py                    # 默认：入场① + 四阶段曝险
factor-layer/.venv/bin/python run_tugboat.py --no-exposure      # 对照：关掉四阶段
factor-layer/.venv/bin/python run_tugboat.py --entry-mode pullback
factor-layer/.venv/bin/python run_tugboat.py --vcp              # 变体：只挑 VCP 形态
```

**`run_tugboat.py` 在仓库根，这是故意的**：它要同时用 `factor-layer`（面板+因子）
和 `backtest`（模拟器+策略），而**两层互不 import 是铁律** ⇒
**组装必须发生在最上面**。它不是某一层的一部分。

**它替你处理了三件容易错的事**（都会**打印出来**）：

| 你不用想 | 它怎么做 |
|---|---|
| 该用哪天的票池？ | 自动取库里**最后一个有像样票池**的交易日（避免 `stocks()` 静默返回 1 只）|
| 起点要多早？ | 默认 `2022-05-03`（票池成型那天）—— **更早的日子只有 16 只，构不成截面** |
| 成本是多少？ | 印在报告头部 —— 改它 = 改实验 |

**它产出的报告里有三条最该看的**（缺了就会读错）：

| 看什么 | 为什么 |
|---|---|
| **`beta` 与「IR（剥离 beta）」** | 行业统计：中位策略对 SPX 有 +0.17 beta，剥离后 IR 从 0.37 掉到 0.21 ⇒ **不剥离就是把行情当本事** |
| **`收益集中度`（Top-5 占多少）** | Top-5 占 >100% ⇒ **拿掉最好 5 笔就是亏的**，结论撑不住 |
| **蒙特卡洛的「重采样后仍赚钱的比例」** | 比"总收益"更能说明**有多依赖运气** |

> ⚠️ **必须配"随机入场"参照**，否则数字没法读：
> **随机选股也会赚**（实测：同一套出场规则下，随机入场中位 +13.36%）。
> ⇒ 只有"真实 vs 同日同数量的随机"那个差值，才**只剩选股的贡献**。
> 实测那次：真实 +19.08% **只到随机的 70 分位**（门槛 95%）⇒ **选股无可辨识贡献**。

### B1. 已有哪些策略

```bash
cd backtest
python3 run_backtest.py --list-strategies     # 实测输出：momentum / regime_gated_momentum
```

加策略 = 照 `backtest/strategies/` 的写法加一个文件（注册表制，同 §A1 的思路）。

### B2. 跑

```bash
# 真实数据（走 provide 契约取数）
python3 run_backtest.py --symbols AAPL MSFT --strategy momentum

# 合成数据（**只验证代码，不可判断策略**）
python3 run_backtest.py --synthetic --symbols SPY QQQ --strategy momentum --synthetic-bars 600 --seed 42
```

**没有** `--cost` / `--start` / `--end` 之类的参数 —— 成本与阈值都在 `backtest_config.py` 里**写死**
（这是**故意**的：判据不可随手调）。

### B3. 怎么读判定

输出是**每个标的一段审计报告** + 一行汇总：

```
  评估 bar 数   : 1422（总 1482，前 60 根 warm-up 不计）   每年 bar 数: 251   ← ★ 年化因子自动估计
  年化 / Sharpe / Sortino / MDD / 多空占比 / 交易笔数
  前后半段年化  : H1 … H2 …          ← "换一段时间还成立吗"
  分段为正      : 1/5 段
  2x 成本年化   : …                  ← "扣掉成本还成立吗"
  判定          : VALID / SUSPICIOUS / INVALID
    ! 每条没过的硬规则都列出来      ← ★ 看这里知道**为什么**没过
```

**三档**（8 条硬规则写死在 `backtest_config.py`，**不可调**）：

| 档 | 含义 |
|---|---|
| `VALID` | 8 条全过 |
| `SUSPICIOUS` | 过了但**可疑**（Sharpe 偏低 / 单边占比过高 / 回撤偏大…）|
| `INVALID` | 有一条硬线没过（年化 < 2% / 分段全负 / 2x 成本下亏损…）|

实测（2026-10-08，`momentum`）：**AAPL / MSFT 都是 `INVALID`** ——
这**不是**"回测坏了"，是 `momentum` 这个玩具策略本来就没优势。

### ⚠️ 坑 4：门禁口径**必须带 `-t .`** —— 否则函数式测试全在门外

> **本节于 2026-10-09 改写**：原「坑 4」讲的是**模块名与标准库同名**（shadowing），
> 而那个模块（原 `backtest/statistics.py`）**已改名 `panel_statistics.py`（TD-05-18）**
> ⇒ **同名问题已消除**。真正剩下的坑只有一条 —— 就是下面这条。

实测（`momentum` 那次，2026-10-08）：

| 命令 | 结果 |
|---|---|
| `python3 -m unittest discover`（不带 `-s`）| ⚠️ **0 项** |
| `python3 -m unittest discover -s tests` | ⚠️ **39 项** —— **只收到 `TestCase`，函数式的 72 项全在门外** |
| ★ `python3 -m unittest discover -s tests -t .` | ✅ **162 项**（**这才是门禁口径**；数字随测试增长而变）|

**根因**：本层大多数测试是 `def test_x() -> bool` **函数式**，而 `unittest discover`
**只收 `TestCase` 子类** ⇒ 它们**一个都进不了门禁**。
（已用 `tests/__init__.py` 的 `load_tests` 协议收口。）

### ⚠️ 坑 5：门禁口径**必须带 `-t .`** —— 否则 72 项在门外

```bash
cd backtest
python3 -m unittest discover -s tests -t .   # ✅ 117 项（**唯一正确的门禁口径**）
python3 tests/run_all.py                     # 同样的 117 项，带一张可读的表
```

**为什么 `-t .` 是必需的**：`tests/__init__.py` 里用 `unittest` 的 **`load_tests` 协议**
把函数式测试也收进来，而**包级 `load_tests` 只有在 `tests` 被当作"包"导入时才会被调用**
—— 那要求 `-t`（top-level）指向 `backtest/`，而不是 `tests/`。

> **★ 这个坑在本仓库犯过两次**：`test_causality.py` 的 docstring 里记过一次
> （"V9 曾经是名义上的 auto：测试存在、门禁不执行"），
> 而我在新写的 5 个文件（含最关键的 simulator / causality / metrics）上**又犯了一次**。
>
> ⇒ **教训**：新写测试时，**第一件事是确认它在门禁口径下真的被跑到**
> （数一下 `Ran N tests` 的 N 有没有变）。**"单独跑全过"和"进门禁"是两回事。**

## 4. 两条路线都要守的纪律

| # | 纪律 | 落地方式 |
|---|---|---|
| 1 | **预注册**：规则/参数**看结果之前写死** | 阈值钉进契约 + **测试断言默认值**（改了立刻红）|
| 2 | **一次跑多个变体 ⇒ 多个 p 值必须一起过 BH** | 判决只经既有的 BH 出口，**无裸判路径** |
| 3 | **幸存者偏差必须显形** | 报告里带 M1 的 `universe_diagnostics` 告警；「不显著」可信、「显著」不可信 |
| 4 | **成本口径显式、两侧一致** | `cost_rate` 必填无默认；两侧同扣 |
| 5 | **近似要显形** | 票池用晚于该日的快照 ⇒ `snapshot_is_after_day=True`，报告不许 paper over |
| 6 | **原文给的区间/歧义 ⇒ 参数化，并**显式定案** | 别**偷偷替他挑一个**。参数进指纹；**默认值钉进测试**（改了立刻红）；定案理由写进 docstring；要跑变体 ⇒ 当**独立实验**、一起过 BH |

> **例（11.5 条件①）**：原文「每日变化 <3，且**累计变化** ≤5」——
> "累计"有 `net`（净变化）与 `path`（逐日绝对变化之和）两种读法。
> 定案取 **`path`**：只有它真的测"RSI 没动"（`net` 会放行来回震荡的票，
> 与规则自己的前提矛盾），且它是 `net` 的子集 ⇒ **更保守**。
> 两种读法都实测过（`path` 75% 的日子有命中 / `net` 93%），差异是**结论级**的。

**口径的选择**（两个都做过，别在旁边另造一个）：

| 口径 | 用哪 |
|---|---|
| K 线 | **hfq**（后复权）。实测 `BMNR` 的 260 日涨幅 **raw 73.6× vs hfq 5.6×**；`AXTI` 两者相同（无复权事件）|
| 标签 | 全仓唯一实现点 `evaluate/forward_return.py`（**别自己写**）|
| 票池 | 只经 `read_stocks(day)`（**别自己判断代码前缀**）|
| 聚簇区间 | 已有观测的不确定性 → `backtest/panel_statistics.py::clustered_interval` |
| 随机对照 | 构造零假设 → **本手册 §2 A**（两者**不互相替代**）|

## 6. 已知的坑（都踩过，别再踩）

| # | 坑 | 症状 / 代价 | 怎么避 |
|---|---|---|---|
| 1 | 用没有快照的交易日取票池 | **静默返回 1 只**，后面全建在 1 只上 | 取票池前 `stocks --day` 验一下 |
| 2 | 面板窗口忽略最长预热期 | 400 天面板 ≠ 400 天样本（260 预热 ⇒ 只剩 139）| 窗口 = 想要的天数 + 最长预热期 |
| 3 | 命中数太少时的噪声 | 每天选 1–2 只 ⇒ 排位极不稳 | 报告里读 `k_per_day_median`，别只看排位 |
| 4 | 只跑 `unittest discover`（不带 `-t .`）| 函数式测试**全在门外**（看着绿其实没跑）| 门禁口径用 `python3 -m unittest discover -s tests -t .` |
| 5 | 只跑 `unittest discover`（不带 `-t .`）| 漏掉全部函数式测试（含 `test_performance_metrics`）| 见坑 4 —— 已由 `tests/__init__.py` 的 `load_tests` 收口 |
| 6 | 忘了 `import evaluate.placebo.implementations` | `注册表为空` 报错 | 注册是**显式动作**（与 `factor.implementations` 同款设计）|
| 7 | 把"均线值"当因子登记 | 它会被 `alpha_factors()` 排除（`screening`）—— 若误标成 `alpha`，会产出一批假阳性 | 均线**值** → 登记**距离**；`role` 选 `screening` |
| 8 | 用 `grep` 做代码级检查 | 命中 **docstring 里写的禁令** ⇒ 误报 | 用 **`ast` 级**（剥掉字符串常量）+ **阳性对照** |
| 9 | 改因子/规则后不跑对应测试 | warm-up / 形状 / 口径三类错**都不会自己报**，只会让结论失真 | 每层都跑一遍（数量会漂移，**以全绿为准**）|
| 10 | **规则模块忘了写 `register_selection(...)`** | `__init__.py` 明明 import 了它，**代码看起来完全正常**，但注册表是空的 ⇒ `get_selection()` 报"注册表为空" | 照 `factor/implementations/*.py`：**文件末尾必须有 `register_selection(...)`**；已有测试盯着（`test_importing_implementations_registers_the_rule`）|

## 7. 一次完整验证的**顺序清单**（照抄即可）

- [ ] **9** 只有 A 过了，才值得进 B（§3）
