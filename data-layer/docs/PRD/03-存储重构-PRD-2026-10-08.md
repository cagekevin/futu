## 一、问题（实测，不是推演）

### 1.1 现状布局与它的代价

```
data/<交易日>/<标的>.<数据项>.json        ← 一个 (标的, 数据项, 交易日) 一个文件
```

| | 逻辑大小 | 实际占用 | 膨胀 |
|---|---|---|---|
| 单文件（`AA.kline.json`）| **199 B** | **4,096 B** | **20×** |
| 全库（345,615 个文件）| **93 MB** | **1.4 GB** | **15×** |

**根因**：一个文件吃一整个 **4KB 块**，而数据只有 199 B ⇒ **95% 是块对齐浪费**。

**外推到全市场**（9,036 只 × 4,478 天）：**4,046 万文件 / ~164 GB** —— POSIX 撑不住。

### 1.2 范围：只迁 `kline`（97.4% 的文件）

| 数据项 | 文件数 | 占比 | 处置 |
|---|---|---|---|
| **`kline`** | **345,615** | **97.4%** | ✅ **迁列式** |
| `adjust_factor` + 10 个 GEX 项 | 9,092 | 2.6% | 保持 JSON |
| `plate_state` / `industry_state` | 46 | 0.01% | 保持 JSON（**带嵌套**）|
| `calendar` / `snapshot` / `plate_list` / `plate_members` | 56 | 0.02% | 保持 JSON |
| `chain` | 9 | 0.003% | 保持 JSON（**只有 9 个文件，迁它没收益**）|

> **97.4% 的问题出在一种数据上，就只改它。** 其余 19 种合计 **9,133 个文件 / 36 MB**，
> 根本不构成问题 —— **少动一样东西就少一份风险**（承「准确性 > 复杂度」）。

## 二、★ 完整链路（**这次重构的核心依据**）

> 前两版方案都错在**没有把链路走完就下结论**：
> 第一版照抄 kdb+ 的「按天」但没问为什么；第二版被"不改调用方"诱惑选了「按标的」，
> 却没算「每天全标的都更新」的写放大。**这一节是防再犯的地基。**

### 2.1 数据怎么**产生**（9 个写点，全部走完）

| 形状 | 写点 | 调用 |
|---|---|---|
| **一天一批**（`put_many`）| `pipeline.py:162` GEX 指标 | 多标的 × 多 item，**一天一次** ✅ |
| **一天一次单点** | `:212` calendar / `:420` plate_list / `:461` snapshot / `:516` industry_state / `:433,:553` 板块（逐板块）| 一天 1–262 次 |
| **⚠️ 逐标的 × 逐天单点** | **`:344` kline** / `:242` adjust_factor | **同一天被写 N 次** |

**kline 的产生路径**：

```
for sym in symbols:                      ← 外层：标的（REST 一次拉一个标的的全历史）
    res = fetch_kline(sym, since=...)
    by_day = 按交易日分组(res.rows)
    for d in by_day:                     ← 内层：天
        axis.put(d, sym, "kline", payload)
```

⇒ **两个事实同时成立**（这是全部设计的关键）：

| 事实 | 含义 |
|---|---|
| 数据**按标的到达**（REST 接口是按标的的）| 写入的**自然单位**是标的 |
| **每天全标的都更新** | 落盘的**自然批次**是「天」 |

**若按标的存**（一标的一文件含全历史）：每天要重写全部历史
= 9,036 只 × 4,478 天 × 7 列 × 8 B ≈ **2.26 GB/天** ⇒ **写放大 4500 倍** ❌

**若按天存**（一天一文件含全标的）：每天写 1 个文件 ≈ **0.5 MB** ✅

### 2.2 数据怎么**读**（走完）

| 接口 | 实现 | 形状 |
|---|---|---|
| `provide.api.panel(symbols, item, days)` | `for s in symbols: series(s, item, days)` + `for s: series(s, 'adjust_factor')` | **按标的循环** ⚠️ |
| `provide.api.align_panel(...)` | 同上 | **按标的循环** ⚠️ |
| `provide.api.timeseries(symbol, item, days)` | `series(symbol, item, days)` | 单标的 |
| `matrix(day, items, symbols)` | — | 单日 |
| `get` / `symbols` / `items` / `days` / `latest_day` / `exists` | 转发 `store` | 枚举 / 单点 |

**现状的真实代价**：一次 `panel(270 只, 1500 天)` = **270 × 1500 = 40.5 万次文件读**（实测 44s）。

⇒ 按天存**必须同时改 `panel()` 的实现**，否则它仍是 40.5 万次读，**等于白改**。

### 2.3 消费者清单（核实过）

| 消费者 | 依赖方式 | 受本次重构影响 |
|---|---|---|
| `factor-layer` | `provide.cli panel/align` | ❌ 不受影响（契约层）|
| `backtest` | `provide.cli align`（`data_source.py`）| ❌ 不受影响（契约层）|
| `frontend` | 无 | ❌ |
| `data-layer/tests/test_store.py` | **直接查 `*.json`**（5 处）| ⚠️ **要改** |
| `data-layer/tests/verify_adjustment_formula.py` | **直接拼文件名**（1 处）| ⚠️ **要改** |

**⇒ 物理布局被 `store/` 完整封装**（承 **P4**）：
`fetch/` / `engine/` / `provide/` / `pipeline.py` **全都不知道文件长什么样**。

## 三、漏洞清单（**21 条**，逐条给处置）

### A. 写入侧

| # | 漏洞 | 严重度 | 处置 |
|---|---|---|---|
| **A1** | kline 是「逐标的 × 逐天」单点写 ⇒ 按天存会被写 **N 次/天** ⇒ **O(N²)** | 🔴 | **改 `pipeline.py` 攒批** |
| **A2** | `adjust_factor` 同样是逐标的 × 逐天 —— 但它**保持 JSON**（稀疏 8,983 文件）| ✅ | **不动** |
| **A3** | `put_many` 的**批原子**语义：改后 kline 走 parquet、其他走 JSON ⇒ **两类文件** ⇒ 必须"先全部落临时、再统一 rename" | 🟠 | `write.py` 支持跨两类文件的批原子 |
| **A4** | **并发写**：按天存后"一天一个文件"⇒ 两进程同写会**互相覆盖**（现状一标的一文件不冲突）| 🟠 | **待你定**（约定单写者 / 加锁）|

### B. 读取侧（按天存后**会变慢**的 9 处）

| # | 漏洞 | 缓解 |
|---|---|---|
| **B1** | `panel()` / `align_panel()` 是 `for s: series(s)` ⇒ **不改就白改** | **必须改**（一次读 M 天 + 按 symbol 分组）|
| **B2** | `series(sym, item, days)` 要读 M 个文件、每个只取 1 行 | 列裁剪 + 按 symbol 分 row group |
| **B3** | `series(sym, 'adjust_factor')`（**不带 days**）遍历全量 `list_days()` | 只读 `ex_div_date` 列 |
| **B4** | `latest_day(sym, item)` **每天每标的**调用（增量起点）| 只读 `symbol` 列 |
| **B5** | `symbols(day)` 靠扫文件名 ⇒ 要**合并** JSON 文件名 + parquet 的 symbol 列 | — |
| **B6** | `items(day, sym)` 要判断"该 symbol 是否在该天 parquet 里" | 只读 `symbol` 列 |
| **B7** | `days()` 要**合并**日期目录 + parquet 文件名 | — |
| **B8** | `exists(day, sym, item)` 同理 | — |
| **B9** | `pipeline.py:267` 的 `get(day, sym, 'kline')` 读 `fetched_at`（**每天 × 328 只**）| 只读 2 列 |

### C. 数据侧

| # | 漏洞 | 处置 |
|---|---|---|
| **C1** | 库里已有 **345,615 个 `*.kline.json`** | **一次性迁移**（用户已确认）|
| **C2** | 回滚：旧 JSON **不删**可回滚；但**必须保证改后不再写旧路径**（否则两处不一致）| 写死 + 测试 |
| **C3** | ★ **类型往返**：bar = `int/str/float`（实测），meta = `int/str/int`（实测）| **测试锁死逐位相等** |
| **C4** | ★★ **`None` ↔ 缺字段的往返不等**：JSON 里**没有** `volume` 这个 key ⇒ parquet 是 `NULL` ⇒ 读回是 `NaN`（**多了一个 key**）| **迁移前置校验**：所有 bar 必须有全部 7 字段，否则报错 |
| **C5** | **每天恰好 1 根 bar**（实测 323/323）| 迁移时**校验**（多根 → 报错）|
| **C6** | bar 字段现在是**隐式契约**（由 pipeline 构造时决定）| 改为**显式清单** `KLINE_BAR_COLUMNS`，多字段 → **报错**（不静默丢）|

### D. 契约侧

| # | 漏洞 | 处置 |

## 四、方案

### 4.1 新布局

```
data/panel/kline/<交易日>.parquet     ← 一天一个文件，含当天全部标的
                                       列 = symbol + bar 字段 + meta 字段（每行重复）
data/<交易日>/<标的>.<数据项>.json     ← 其余 19 种，**原样不动**
```

**列**（显式声明，承 C6）：

```
symbol | ktype | as_of | fetched_at | time_key | date | open | high | low | close | volume
         └────────── meta（每行重复 —— 不假设"全标的相同"，那种假设迟早出错）──────┘
```

> **为什么不把 meta 放进 parquet 的 schema metadata**：`fetched_at` **每只标的可能不同**
> （不同时间拉的）⇒ 放行里才正确。

### 4.2 ★ 必须同时改的 **4 处**（不是"零改动"）

| # | 改什么 | 对应漏洞 | 规模 |
|---|---|---|---|
| **1** | `pipeline.py` 的 kline 写入**攒批** | A1 | ~20 行 |
| **2** | `provide.api.panel()` / `align_panel()` 的**读取**改成「按天读 + 分组」 | B1 | ~60 行 |
| **3** | `store/read.py` 的 6 个枚举/单点函数（合并两处 + 列裁剪）| B3–B9 | ~80 行 |
| **4** | `store/write.py` 的**跨两类文件**批原子 | A3 | ~60 行 |

### 4.3 迁移方案（**一次性**）

```
1. 前置校验（不通过就停）：
     · 所有 bar 有全部 7 个字段（承 C4）
     · 每天恰好 1 根 bar（承 C5）
     · 标的名合法
2. 读全部 345,615 个 *.kline.json → 按天聚合
3. 写 4,478 个 data/panel/kline/<day>.parquet（zstd）
4. **逐位比对**：新读法 vs 旧读法，同一批 (symbol, day) 必须完全相等
5. **旧 JSON 目录不删**（回滚路径，承 C2）
6. 改 PARQUET_ITEMS 为空即回滚
```

**运行时间**：**~2 分钟**
（依据：实测读数速度 **0.074 ms/文件**（40.5 万文件读 30s）× 34.6 万 ≈ 26s；
加 JSON 解析 + 写 4,478 个 parquet ≈ 90s）

### 4.4 验收标准（承 X10）

> **不是"用了 parquet"，而是「`store` 的公开接口行为逐位不变」。**

| # | 验收 | 方法 |
|---|---|---|
| 1 | `store` 既有测试全绿 | `tests/test_store.py` |
| 2 | **往返逐位相等** | 新增：JSON → parquet → 读回，逐位比对 |
| 3 | **`provide` 输出逐位不变** | 改前 / 改后跑同一批 `panel`/`align` 请求，比对 JSON |
| 4 | 文件数 | 345,615 → **4,478** |
| 5 | 磁盘 | 1.4 GB → **几 GB 以下** |
| 6 | `panel(270, 1500)` 耗时 | 44s → **目标 <5s** |
