## 三、三个候选能力

### 3.1 N1 —— 基本面指标（**建议 P0**）

**来源**：REST（`vendor/futu-src/fetch/rest/fundamentals.mjs` 的路径规律：`/api/v1.0/quote/{symbol}/<分类>/<名称>`）

| 拉取项 | 路径 | 参数 | 拿到什么 |
|---|---|---|---|
| `metrics` | `financials/statements` | `statement_type=4, limit=4` | **ROE / 毛利率 / 净利率 / 负债率**（4 期）|
| `pe` | `valuation/detail` | `valuation_type=1` | PE + **历史分位 `valuation_percentile`** |
| `pb` | `valuation/detail` | `valuation_type=2` | PB + 历史分位 |

**可解锁的因子**（与现有 7 个量价因子**原理上正交**）：
`roe` / `gross_margin` / `net_margin` / `debt_ratio` / `ep`(=1/PE) / `bp`(=1/PB) / **估值分位**

**代价**：270 只 × 3 次 = **810 次请求**（一次性）；**季度频率** ⇒ TTL 7 天足够，**不该天天拉**。

**★ 本项最大的坑：point-in-time（必须写进约束，见 §4）**

财报有**两个日期**：**报告期**（如 2026Q1 = 2026-03-31）与**公告日**（如 2026-04-28）。
用**报告期**做历史截面 = **前视**（3 月 31 日那天，市场还不知道这份财报）。

⇒ **必须同时存「公告日」与「报告期」，下游按公告日对齐。**
⚠️ 若该接口**不返回公告日**，则 N1 的**历史回测价值大打折扣**（只能做"当前截面"）
—— **这一点必须先做小样本验证，不能假设**。

### 3.2 N2 —— 事件类（**建议 P1，先验证可行性**）

| 拉取项 | 路径 | 拿到什么 | 风险 |
|---|---|---|---|
| `consensus` | `research/analyst-consensus` | 分析师目标均价 / 最高 / 最低 / 评级分布 | ⚠️ **很可能是"当前快照"** —— 无历史 ⇒ 做不了"预期修正"因子 |
| `dividends` | `corporate-actions/dividends` | 分红派息历史 | 与已有 `adjust_factor` **可能重叠** |
| `splits` | `corporate-actions/splits` | 拆合股历史 | 同上 |

**两个必须先查清的问题**：

1. **历史可回溯性**：`consensus` 是否有历史？若无 ⇒ **只能做当前截面因子，且无法回测**（价值大幅下降）。
   ⇒ **建议先花半天做小样本验证**，再决定是否立项。
2. **与 `adjust_factor` 的重叠**：`dividends` / `splits` 与现有复权因子表**是否同源**？
   ⚠️ 若是 ⇒ **两份真相**（承本仓铁律：「两处都能改 = 迟早对不上」）⇒ 要么**不拉**，要么**明确谁是真源**。

### 3.3 N3 —— 扩大票池（**建议 P2；但它的前置是「存储重构」，不是「取数」**）

**现状差距**：票池 **270** / 全市场 **9,036**（33 倍）。

> ⚠️ N3 的**收益是最大的**：票池 270 → 9000 会**同时**解决
> ①**幸存者偏差**（现在库内 0 只退市样本，承 factor-layer §9.1 ④）
> ②**行业分组样本量不足**（现在 68 个行业里只有 30 个达到阈值 3）
> ③**统计功效**（截面从 270 只变 9000 只）

#### 3.3.1 真正的拦路虎：**一个文件吃一个 4KB 块**（实测）

| | 逻辑大小 | 实际占用 | 膨胀 |
|---|---|---|---|
| 单文件（`AA.kline.json`）| **199 B** | **4,096 B** | **20×** |
| 全库（345,615 个文件）| **93 MB** | **1.4 GB** | **15×** |

⇒ 全市场外推：**数据 ~11 GB，磁盘 ~164 GB，文件 4,046 万个**。

**两个问题要分开解决**：
- **空间** → 换列式格式（拿回 15×）
- **文件数** → **必须分区**（4046 万文件，任何格式都撑不住）

#### 3.3.2 行业怎么做（查证，非记忆）

| 参照 | 做法 |
|---|---|
| **kdb+**（银行/对冲基金事实标准）| 按**天**分区（`my_hdb/2026.04.17/trades/`）+ **列式**（每列一个物理文件，`.d` 存列名）⇒ 读只碰需要的列；**历史分区只读**；冷热分离 |
| **ArcticDB**（Man Group 孵化 + Bloomberg 共建）| **"Bitemporal versioning"（双时态版本化）** —— 每次写入生成新版本，支撑 **point-in-time 查询 / 研究可复现 / 历史修正**；append = 追加新段 + 后台 compact；客户端直连存储（serverless）|
| 行业核心概念 | **Point-in-Time (PIT) Data** —— 存"在当时那天已知的样子"，**不带后续修正**，消除 look-ahead 与 **restatement bias** |

#### 3.3.3 ★ 本仓的存储模型**已经是对的**，只缺"版本显形"

```
kline          存 raw        ← 除权不改它 ⇒ 【天然不可变】✅
adjust_factor  事件表         ← 追加 = 新事件，不是改旧事件 ✅
复权结果        派生量，不存   ← 【不落盘】✅
```

这三条正是行业原则的特例。缺的只是**把版本显形**：

| 现状 | 问题 |
|---|---|
| `panel --adjust hfq` | 用**最新**的 `adjust_factor` 算 ⇒ **不可复现** |

**轻量修法（不改存储布局）**：加 `--adjust-as-of <日期>`，只用 `ex_div_date ≤ 该日` 的事件
⇒ **只要 `adjust_factor` 保证「只追加、不修改」，PIT 就是免费的**（承 X8）。

#### 3.3.4 ★ 详细设计已独立成文

> **`03-存储重构-PRD-2026-10-08.md`** —— 本文只保留"为什么立项"，
> **方案 / 完整链路 / 21 条漏洞清单 / 迁移与验收全部在那份**（避免两份真相）。

**选型结论**（详细对比见 03 号文）：

| 方案 | 文件数 | 新增安装 | 列式 | 结论 |
|---|---|---|---|---|
| **parquet（选定）** | ~4,478（**一天一个**）| **0（pyarrow 已装）** | ✅ | ✅ |
| SQLite | 1 | 0（stdlib）| ❌ 行式 | 次选 |
| DuckDB | 1 | 1 个小包 | ✅ | 需要 SQL 时加 |
| ArcticDB | 自管 | 1 个**大**包 | ✅ | **不上**（见下）|
| ~~Polars~~ | — | 1 个包 | ✅ | ❌ 要改上层 DataFrame 库 |

**★ 为什么不上 ArcticDB**（修正本文早期版本的判断）：

它的**唯一独特价值是"版本化"**，但 §3.3.3 已证明 ——
**只要 `adjust_factor` 只追加不改，PIT 就能免费自建**（`ex_div_date ≤ T`）。
⇒ 增量价值**不足以抵消**「大包 + 格式黑盒 + 数据锁在库里」。
**除非**将来需要「多版本并存 + 数据被修正后要能回滚」，那才值得上它。

> ⚠️ **许可澄清**：ArcticDB 是 BSL 1.1，但官方明确
> **"free for non-commercial, personal, or academic use"**，且各版本两年后转 Apache 2.0。
> **个人使用不受限** —— 不上它是因为**技术取舍**，不是许可。

#### 3.3.5 必须写进约束的一句话

> **格式换了，`Key` 三元组的语义不能换。**
> `(交易日, 标的, 数据项)` 是**唯一真相**，物理布局只是它的**一个投影**。
> 重构的验收标准不是"用了 parquet"，而是**「`store/` 的公开接口行为逐位不变」**。

## 四、约束（若立项，必须满足 —— 全部沿用既有铁律）

| # | 约束 | 出处 |
|---|---|---|
| **X1** | **源名不外泄**：REST 代码放 `fetch/sources/`（已在），`store/` `engine/` `provide/` 不得出现源名 | 承 **F1** |
| **X2** | **失败必报**：断网 / 签名失效 / 返回结构不符 → 抛错，**不静默返回空** | 承 **F4** |
| **X3** | **新数据项必须登记** `KNOWN_ITEMS`，否则 `store.put` 报错 | 承 **K3** |
| **X4** | **进 `PULL_ITEMS` 必须声明频率**：季度数据**不许天天拉**（`--ttl` 机制）| 承 **L** |
| **X5** | ★ **point-in-time 铁律**：任何带「公告日」的数据，**必须同时存公告日与报告期**；下游按**公告日**对齐。若接口不返回公告日 → **显式声明"此项无法用于历史回测"**，不许假装 | 承 **P5** + factor-layer 的 Q2/Q4 |
| **X6** | **不许两份真相**：新数据项与既有项（如 `adjust_factor`）若语义重叠 → 先定**谁是真源**，另一个要么不拉、要么显式标注为派生 | 承 **SSOT** |
| **X7** | **近似必须显形**：若用"当前快照"近似历史（如 `consensus`），返回里必须带标记 | 承 **P5** |
| **X8** | ★ **历史不可变（PIT 的地基）**：**`adjust_factor` 一旦写入，不许修改**（除权事件是历史事实）。若数据源修正了历史事件 → **新增一条**并显式标注，不许覆盖 | 承 **§3.3.3** + 行业 **PIT** 原则 |
| **X9** | ★ **查询必须能声明 as-of**：`panel` / `align_panel` 的 `--adjust` 增加 `--adjust-as-of <日期>`，只用 `ex_div_date ≤ 该日` 的事件 ⇒ 复现"我在那天看到的复权价" | 承 **§3.3.3** |
| **X10** | ★ **存储重构的验收不是"用了 parquet"**，而是**「`store/` 的公开接口行为逐位不变」**；且必须留**回滚路径**（旧目录先不删）| 承 **P4** + 铁律 6 |

## 五、风险清单

| # | 风险 | 严重度 | 处置 |
|---|---|---|---|
| **R1** | **N1 的 point-in-time**：接口若不返回公告日 ⇒ 基本面因子**无法用于历史回测** | 🔴 高 | **先验证**（小样本，半天），再决定是否投入 |
| **R2** | **N2 的历史可回溯性未知**：`consensus` 很可能只有当前值 | 🟠 中 | 先验证；若无历史则**降级为"当前截面因子"**并显形 |
| **R3** | **N2 与 `adjust_factor` 重叠** → 两份真相 | 🟠 中 | 立项时先比对同源性与数值一致性 |
| **R4** | **N3 的存储重构**：不可逆架构决策 | 🔴 高 | **单独立项**；先做格式选型与迁移方案 |
| **R5** | **REST 凭据在仓库外**（`~/.config/futu/`，chmod 600）⇒ 新机器 / CI 需单独配 | 🟡 低 | 已在 `rest_source.py` 里显式声明；文档补一句即可 |
| **R6** | **季度数据的"未来函数"陷阱**：即使有公告日，**同一份财报在公告后会被修正**（restatement）| 🟠 中 | 承 X5：显形，不掩饰 |

## 六、建议的优先级与代价

| 优先级 | 项 | 前置 | 代价 | 解锁 |
|---|---|---|---|---|
| **P0** | **N1 基本面**（metrics + pe + pb）| 验证 R1（半天）| 810 次请求 + 一个 `fetch_fundamentals` 方法 + 3 个 `KNOWN_ITEMS` | **6–7 个新因子**（ROE / 毛利 / 净利 / 负债率 / EP / BP / 估值分位）|
| **P1** | **N2 可行性验证**（不是实施）| — | **半天**（只查历史可回溯性 + 与 `adjust_factor` 的重叠）| 决定 N2 是否值得做 |
| **P2a** | **N3 阶段 0：存储 spike** | — | **半天**（不写生产代码，只量数字 + 验逐位相等）| 决定 parquet 是否真的更快更小 |
| **P2b** | **N3 阶段 1：换引擎** | P2a 通过 | 改 `store/` 3 文件 + 迁移脚本 + 回滚路径 | 文件数 4046 万 → ~4500；磁盘 164 GB → ~几 GB |
| **P2c** | **N3 阶段 2：扩票池** | P2b 完成 | 取数（REST 无额度）| 根治幸存者偏差 + 行业样本量 + 统计功效 |

**★ 执行顺序（2026-10-08 用户决定：存储优先）**：

```
① P2b 存储重构（见 03-存储重构-PRD）—— 现在做
     理由（用户）：现在是 34.6 万文件，迁移快；等扩到 4000 万文件再迁，代价高一个数量级
② P1 验证（半天，最便宜，且决定 N2 的生死）
③ P0 的 R1 验证（半天，决定 N1 的历史价值）
④ 两项验证都通过 → N1 实施（1 天）→ 拿到 6–7 个基本面因子
⑤ 用基本面因子再跑一次 factor-layer —— 若仍不显著，再谈 P2c 扩票池
```

> **为什么存储可以提前**（我原先建议排最后，用户判断更优）：
> 它的**代价随数据量线性增长**（迁移 = 全量重写），而**收益是立刻的**
> （`panel()` 40.5 万次读 → 1,500 次）。**越早做越便宜。**
>
> ⚠️ 但它是唯一**不可逆**的一步 ⇒ 所以必须有 **03 号 PRD 的完整链路 + 21 条漏洞清单**
> 与**回滚路径**（旧 JSON 不删）兜底。
>
> **P0 仍然是风险最低的一步**（纯增量，不动现有任何东西）——
> 但"低风险"不等于"该先做"：存储的**窗口期**是数据量小的时候，**错过就没了**。
